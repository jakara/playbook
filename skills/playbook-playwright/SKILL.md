# Playbook ↔ Playwright

把一段业务流程用于演示与测试。Playbook 负责讲解和编排，Playwright 继续负责原生交互与断言。业务脚本留在业务仓库；不要把客户脚本、凭据或运行证据写入 Playbook 产品仓库。

## 开始时

读取目标 TC 或 `.playbook.ts`，沿实际 import 查阅 fixture、helpers、Playwright 配置、setup/teardown 与环境选择。不要只处理测试函数的正文。先确认用户要求的是共享流程还是可独立运行的导出；未指定时首选共享流程，避免两份业务逻辑漂移。

读取 [契约](references/contract.md)，再按方向读取 [TC → Playbook](references/tc-to-playbook.md) 或 [Playbook → TC](references/playbook-to-tc.md)。已有项目契约与本 Skill 版本不一致时先识别差异，按项目实际 SDK 适配，不悄悄改写版本。

本 Skill 随附 v0.1 契约说明；`@playbook/core` 是参考 SDK 的本地包名，尚未承诺存在公开 npm 包。先检查目标仓库已有依赖与导出路径，不能凭名字自动安装未知包。

## 语义边界

- 保留 Locator、动作顺序、事件等待、断言预期、账号角色、mock/fixture、数据准备和清理的实际语义。保留原测试，除非用户授权替换；共享迁移可新增 TC 适配入口供对照。
- 讲解、蒙层与阅读时间属于演示元数据，不能代替业务断言或用固定等待修补缺失的结果条件。不要把 `fill`、键盘事件、上传、API 写入等改成“看起来差不多”的操作。
- 区分 real / fixture / mock，声明业务副作用与重播条件；元数据不是安全拦截器，`read-only` 必须由实际路径和运行证据支撑。
- 不把测试专用账号、临时权限、绕过登录、路由 mock 或测试数据库准备默认移植到客户现场。可以忠实保留为模拟演示并标识来源；需要真实服务时另外实现并验证 Profile。
- Playbook 中的代码只描述流程，测试生命周期仍由 Playwright Test 管理，演示登录与环境准备由业务 Profile 提供。不要在共享流程中调用 `test()`、`test.use()`、`test.beforeEach()` 或隐式依赖 TestInfo。
- 动态分支、复杂闭包、自定义 matcher、数据库 fixture 或多页面协作无法直接映射时保留原 helper 依赖并说明适配要求。只阻塞确实依赖缺失信息的部分，不用空函数或 TODO 冒充可运行转换。
- 本 Skill 不授予执行客户数据写入或生产清理的权限。优先在已有隔离测试环境验证；原用例本就包含的写入也要确认运行目标与当前授权一致。

## 交付与验证

交付目标脚本、适用的 TC/环境适配入口，以及按 [报告规范](references/conversion-report.md) 写出的对应关系和验证结果。能从原代码确认的内容自行确定，不要求用户重复提供。

至少进行项目已有的类型/语法检查。具备已授权的隔离环境时，运行原用例与转换后入口，对比关键结果；可行时用一次刻意失败的预期确认断言仍生效。未执行的浏览器、数据恢复或客户环境检查明确列出。

若生成负向用例副本，将它放在正向测试收集目录之外或明确排除；核对实际收集项，避免把预期失败副本混入正向通过结论。

收尾区分：已保留、已适配、需要补齐、实际通过、尚未验证。只有编译通过时不能声称业务等价或客户演示可用。输出具体路径、执行结果和最小剩余动作。
